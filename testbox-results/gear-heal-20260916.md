## Count-truncation check (your 4 desync conditions) — ALL RULED OUT on this box's data

Item fields are `enchantments` and `bonusListIDs` (no gem columns; `item_instance_gems` is a separate table). Real schema `characters`.

- **name > 63 (6-bit):** IMPOSSIBLE — `MAX(LENGTH(name))` across all characters = **11**. (Sellarino = 9.)
- **modifiers > 127 (7-bit):** box-wide `MAX` bonusListIDs element count over all equipped items (bag0 slot<19) = **3**. Zero items exceed 127. (Sellarino's items: 1-3 bonus IDs each, e.g. `6652 12365 12921`.)
- **gems > 3 (2-bit):** `item_instance_gems` table = **0 rows** — no bot has any gems at all.
- **enchants > 15 (4-bit):** the `enchantments` column is uniformly **39 numbers = the fixed 13-slot triplet array** (id,duration,charges × 13), i.e. <=13 active enchant slots, which is < 15. Not 39 enchants.

**Azerite (the field that actually blows up — JamCliAzeriteEssenceData):** all four azerite tables are EMPTY on this box —
`item_instance_azerite`, `item_instance_azerite_milestone_power`, `item_instance_azerite_empowered`, `item_instance_azerite_unlocked_essence` = **0 rows each**. So no inspected bot item carries azerite/essence data; the client is allocating from a count it reads at that offset, which (given no azerite data exists) points to a **bit-cursor desync from an earlier field that is NOT one of the four counted ones** — none of the four are reachable here. The raw packet is the decider; capture still pending agatho's client.
